# 问题台账

只记**真的踩过、会再踩**的问题。没遇到的不写，写完的不重复写。
每条四段：现象 → 根因 → 处置 → 预防（已固化到哪一步）。

---

## 1. 听到的音频切错了位置

| 项 | 内容 |
| --- | --- |
| 现象 | 切完 19 段，只有 11 段首句对得上；有的段开头是上一题结尾 |
| 根因 | 每个小题读两遍、题内也有 1–2 秒停顿；按 `silencedetect` 中点切会把「第一遍/第二遍」劈开 |
| 处置 | 用 Whisper 转写定位，取**录音里念出的题号**（"7." / "Nine" / "Thirteen"）当锚点，切完逐段回读首句比对 |
| 预防 | SKILL.md §5；`scripts/cut_audio.py --verify`；判据：逐段首句全部对得上（个别因音质存疑要单独说明） |

## 4. 上传返回 502 Bad Gateway

| 项 | 内容 |
| --- | --- |
| 现象 | POST 返回 nginx 502 HTML 页面，非 JSON；2026-10-22 这次持续 6 分钟不自愈 |
| 根因 | 两种：①后端重启窗口，②**某线程持未提交写事务**——`cleanup()` 删过期草稿触发 `FOREIGN KEY constraint failed`（`question_layout_locks.question_id` 缺 `ON DELETE CASCADE`），异常在 `db.commit()` 前抛出，连接泄漏并长期持有 RESERVED 锁；此后每个请求的 `cleanup()` 都在 sqlite 默认 5s busy timeout 后失败。**进程没崩 → systemd 不重启 → 一直 502** |
| 处置 | 判据：`curl /api/health` 计时 ≈5.0s 且 `journalctl` 里是同一进程反复报 `database is locked`，即②。处置：备份 db+journal → 修 `cleanup()`（先删 layout lock、逐行 try/except、异常 rollback）→ 重启服务让 hot journal 回滚 |
| 预防 | ISSUES 记录判据；`cleanup()` 已改为事务安全；502 一律先查日志里的真报错，别只怪重启窗口 |

## 10. 环境类报错（报错位置≠真实原因）

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| `pwsh` 无输出、退出码 `3221225794` | 受限沙箱下 PowerShell 起不来，不是命令写错 | 需要 full access |
| `Unexpected UTF-8 BOM` | PowerShell `Set-Content -Encoding UTF8` 写 BOM | 读用 `utf-8-sig` |
| `SaveAs([ref])` 报「值不在预期范围内」 | PowerShell COM 绑定差异 | 用 `SaveAs2($dst, 12)` |
| faster-whisper `metadata_errors` | 新版 `av` 接口不兼容 | ffmpeg 转 16k wav + numpy 传入 |
| scp 中途报错但已传一部分 | 多文件 scp 非原子 | 逐个传 + `ls | wc -l` 点数 |
| 导出图片 `basename` 为空 | zip 里 `word/media/` 含目录条目 | 过滤 `endswith("/")` |
| `subprocess(text=True)` 抛 `UnicodeDecodeError: 'gbk' codec`（线程崩溃、后续 `log` 变 None） | Windows 下 subprocess 默认按 GBK 解码，ffmpeg stderr 含非 GBK 字节 | 显式 `encoding="utf-8", errors="replace"`；或整个进程 `PYTHONUTF8=1` |
| PowerShell `*>` 重定向出的 txt 是 UTF-16LE，`read` 报 binary file | `Out-File`/重定向默认 UTF-16 | 读回后用 `[IO.File]::WriteAllText` 转成 UTF-8 无 BOM |

## 11. 锚点连切把下一大题的中文播报吞进上一段

| 项 | 内容 |
| --- | --- |
| 现象 | 2020 卷切完 9 段，`li-05` 66s、`li-07` 176s，末尾混进「Ⅱ.长对话理解」「Ⅲ.短文理解」的中文题头 |
| 根因 | `cut_audio.py` 的 `--anchors` 语义是「每段起点」，每段一直切到**下一个锚点**；跨大题时两锚点之间夹着 26–36s 的中文题头+长空白。当时误以为是 ffmpeg `-to` 失效 |
| 处置 | 用词级时间戳定出每段真正的末句结束点，改按**显式起止**切；回读首句 9/9 命中、尾句也都落在本段末句 |
| 预防 | `scripts/cut_audio.py` 新增 `--ends`（与 `--anchors` 等长的终点数组，段间可不相邻）；默认行为不变 |

## 13. 内容指纹误判与漏判

| 项 | 内容 |
| --- | --- |
| 现象 | 初版指纹只取题干，把各年通用的「选出一个你所听到的单词或短语」判成同一题；题干尾部改动又因截断 120 字而漏检 |
| 根因 | 通用指令题干重复度高；归一化时截断 |

## 15. 知识点大面积漏标、且标错维度

## 17. 标签只打一个、且有过标错

| 项 | 内容 |
| --- | --- |
| 现象 | 单项填空普遍只挂一个标签；2019 第 31 题是「Well done」的交际用语，却标成「名词辨析」；2020 一批只写到「名词」「副词」「动词」这种粗粒度 |

## 20. 听力切分时 Whisper 时间戳不可靠

| 项 | 内容 |
| --- | --- |
| 现象 | 2021 卷 12 分钟音频，转写给出的分段与真实语音位置错位（如前 35 秒全被标成 "yoo"，"2." 落在静音段中间）；只靠 `--transcribe` 的时间戳切分会把两遍朗读劈开 |

## 21. 附件 placement 写错导致确认静默失败

| 项 | 内容 |
| --- | --- |
| 现象 | 人工点「逐题确认」无反应；服务端日志里 `POST /api/uploads/<id>/confirm` 连续返回 **400**，前端只弹了一句被忽略的提示 |
| 根因 | 音频附件写成 `"placement": "stem"`。服务端 `normalize_attachments` 只接受 `question / option / answer / explanation`，不合法就抛 `ValueError` → 外层统一 400 `invalid_request`。历史批次音频附件根本没传 placement（默认 question），所以从未暴露 |
| 处置 | 全部音频改为 `"placement": "question"`，重新上传；旧暂存作废 |
| 预防 | 上传前用服务端校验器本地回放一遍（附件/知识点/表格三类），不要等人工点确认才发现；确认返回 400 时先看 `journalctl -u mudu-quiz` 与接口实现 |

## 38. 实测各类操作的下限，别再优化错地方

| 操作 | 实测耗时 | 结论 |
| --- | --- | --- |
| SSH 纯往返 / `python3 -c pass` | 0.36s / 0.38s | 每次远程校验有 0.4s 固定成本，**能合并就合并** |
| `import backend` | 0.42s | 同上 |
| 全库 379 行指纹扫描 | 0.02s | 查重**不是**瓶颈，不要为它加缓存 |
| `current_knowledge_points`（522 节点） | 0.002s | 预检的知识点解析也**不是**瓶颈 |
| 20 个 URL 串行 curl / 并发+Range | 6.3s / 1.8s | 网络 RTT 主导，必须并发 |
| 9 个小文件 scp / tar 管道 / 并行 scp | 1.9s / 1.3s / 6.1s | tar 略快但引入临时文件；**并行 scp 因进程启动反而更慢** |
